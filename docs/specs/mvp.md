# Спецификация MVP

Складской контракт и формат интерфейса согласованы 9 ноября 2026 года. Реализация начинается после `GO`. Приёмка включает HTTP API, Swagger UI, демонстрационную страницу, запуск через Docker Compose и тесты на PostgreSQL.

## Общий контракт

- Запись принимает JSON. Идентификаторы и количество — целые числа от 1 до 2 147 483 647. Пустые обязательные поля, неверный тип, дробное, нулевое и отрицательное количество дают `400`. Время операции задаёт сервер в UTC.
- Ошибки возвращаются как Problem Details. Для бизнес-конфликтов поле `code` даёт стабильную причину. При неожиданной ошибке сервер возвращает `500` без внутренних деталей. Провал до фиксации транзакции оставляет данные прежними. Если ответ на приёмку потерян, её можно повторить с тем же номером. Повтор POST резерва создаёт новый резерв при достаточном остатке.
- Списки возвращают JSON-массив. Опциональные `limit` (по умолчанию 50, диапазон 1–100) и `offset` (по умолчанию 0, целое неотрицательное число) применяются после фильтрации и сортировки. Ошибочные параметры дают `400`. Пустой результат — `200 []`. Справочники отсортированы по `id` по возрастанию.
- Для `GET` по идентификатору неизвестный ресурс даёт `404`. Фильтры списков с корректным, но неизвестным идентификатором дают пустой результат.

## MVP-1. Товары

**Поведение и вход.** `POST /api/products` принимает `name` и `sku`, возвращает `201` и `{id, name, sku}`. `GET /api/products/{id}` возвращает один товар. `GET /api/products?q=...` возвращает список. Поиск — буквальная подстрока названия или SKU без учёта регистра, включая названия на кириллице. Пробелы по краям запроса убираются. Пустое `q` означает список без поиска. Максимум для `q` — 120 символов после обрезки.

**Валидация и ошибки.** Название после обрезки содержит 1–120 символов. SKU после обрезки содержит 1–40 символов из набора ASCII `A–Z, a–z, 0–9, ., _, -` и хранится в верхнем регистре. Повтор нормализованного SKU даёт `409 duplicate_sku`. Неизвестный ID — `404`.

**Приёмка.** Созданный товар доступен по ID и в списке. Поиск находит его по части названия или SKU в другом регистре. Символы `%` и `_` не работают как шаблоны поиска. ` box-01 ` и `BOX-01` не создают две записи.

## MVP-2. Склады

**Поведение и вход.** `POST /api/warehouses` принимает `name` и возвращает `201` с `{id, name}`. `GET /api/warehouses` возвращает список, `GET /api/warehouses/{id}` — один склад.

**Валидация и ошибки.** После обрезки название содержит 1–120 символов. Совпадающие названия допустимы, склады различаются по ID. Невалидное название даёт `400`, неизвестный ID при чтении — `404`.

**Приёмка.** Созданный склад появляется в списке и читается по ID. Пустое имя не создаёт запись.

## MVP-3. Приёмка

**Поведение и вход.** `POST /api/supplies` принимает `reference`, `productId`, `warehouseId` и `quantity`. Один номер относится к одной позиции на одном складе. Первая успешная приёмка возвращает `201` с `{id, reference, productId, warehouseId, quantity, createdAt}`, увеличивает `onHand` и добавляет одну запись истории. Повтор того же нормализованного номера и тех же значений возвращает `200` с исходным результатом.

**Валидация и ошибки.** Номер имеет тот же формат и нормализацию, что SKU, и уникален среди всех поставок. Тот же номер с другими товаром, складом или количеством даёт `409 supply_reference_conflict`. Сравнение с существующей поставкой идёт после проверки формата и до проверки существования ссылок. Для нового номера неизвестный товар или склад даёт `404`. Превышение максимального физического остатка для пары даёт `409 stock_limit`.

**Приёмка.** Два последовательных или параллельных запроса с одним номером и одинаковыми данными дают один факт, одно увеличение и одну запись истории. При разных данных с тем же номером фиксируется только победившая запись. Разные номера по одной паре суммируются без потерь, включая первую приёмку по паре.

## MVP-4. Резервирование

**Поведение и вход.** `POST /api/reservations` принимает `productId`, `warehouseId` и `quantity`. При успехе увеличивает `reserved`, оставляет `onHand` прежним и добавляет запись истории. Ответ `201` с `{id, productId, warehouseId, quantity, createdAt}`.

**Валидация и ошибки.** Неизвестный товар или склад даёт `404`. Отсутствующий остаток по существующей паре или `quantity > available` даёт `409 insufficient_stock`. Резерв ровно на всё доступное количество допустим.

**Приёмка.** После приёмки 10 резерв 4 оставляет `onHand=10`, `reserved=4`, `available=6`. Если два запроса одновременно хотят по 7 из 10, только один создаёт резерв и историю. Второй получает `409`, доступно 3. Резервирование на одном складе не меняет другой склад.

## MVP-5. Остатки и история

**Поведение и вход.** `GET /api/stocks` и `GET /api/stock-movements` принимают необязательные `productId` и `warehouseId`. Остатки возвращают `{productId, warehouseId, onHand, reserved, available}` только для существующих строк `Stock`. Порядок — `warehouseId`, затем `productId` по возрастанию. История возвращает `{id, productId, warehouseId, type, operationId, onHandDelta, reservedDelta, createdAt}`. Тип `supply` даёт положительную физическую дельту и нулевую дельту резерва, `reservation` — нулевую физическую и положительную дельту резерва. `operationId` относится к операции указанного типа. Сортировка по `createdAt` и `id` по убыванию.

**Валидация и ошибки.** Некорректный фильтр даёт `400`. Без операций обе выдачи пусты. При двух фильтрах должны совпасть оба.

**Приёмка.** После приёмки 10 и резерва 4 видна одна строка с остатками 10/4/6 и две записи журнала с дельтами 10/0 и 0/4. Фильтры исключают чужие товары и склады. Повтор поставки и отклонённые операции не меняют историю.

## Демонстрационная страница

Одна светлая страница в направлении C из [визуального исследования](../design/research.md). Блоки «Приёмка», «Резерв» и «Результат» показывают один сценарий. Статические HTML, CSS и JS обслуживает тот же ASP.NET Core. Страница обращается к существующему REST API. Все операции API доступны через Swagger UI.

На странице можно выбрать существующие товар и склад из справочников или создать новые, указав название и уникальный SKU для товара. Справочники загружаются через API; загрузка страницы не создаёт данные. Для приёмки указать номер поставки и количество (по умолчанию 10). Для резерва указать количество (по умолчанию 4). Итог показывает актуальные значения «На складе», «В резерве» и «Доступно» из API для выбранной пары. Повтор POST резерва автоматически не выполняется. Swagger UI остаётся доступным для остальных операций API.

**Приёмка.** На новой паре принять 10 единиц, повторить приёмку с тем же номером и увидеть те же 10. Зарезервировать 4 и увидеть итог 10/4/6. При попытке зарезервировать 7 показать понятную ошибку, сохранив итог 10/4/6. Все поля имеют подписи, фокус виден с клавиатуры, страница читается на узком экране.

## Сквозная приёмка

1. Пройти сценарий из [описания продукта](../product.md) через API с чистой базой и проверить контракт по OpenAPI.
2. Подтвердить на PostgreSQL, что при сбое после промежуточной записи откатываются остаток, операция и история, а сценарии гонок сохраняют инварианты. Сценарии перечислены в [стратегии тестирования](../testing.md).
3. С чистого запуска проверить Docker Compose и доступность Swagger UI, прогнать сборку и тесты. Подтвердить результат GitHub Actions, когда доступен согласованный GitHub-репозиторий. При отсутствии доступа сохранить локальные результаты и явно отметить статус удалённой проверки.
4. Пройти критерии демонстрационной страницы на том же стенде.
