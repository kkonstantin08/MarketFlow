# План реализации MarketFlow

**Цель.** Довести складской сценарий от пустой базы до проверяемого MVP.

**Архитектура.** Один API, один тестовый проект и одна БД. [Контракт](specs/mvp.md), [архитектура](architecture.md) и [стратегия тестирования](testing.md) задают границы этапов.

**Стек.** .NET 10, ASP.NET Core Web API, EF Core с Npgsql, PostgreSQL, OpenAPI и Swagger UI, xUnit, Docker Compose, GitHub Actions на Linux.

План вступает в работу после команды `GO`. Чекбокс закрывается после выполнения критерия и проверок. После этапа записывай фактический результат в [progress.md](progress.md) и делай логический коммит. При наличии Superpowers перед кодом разложи очередной этап на конкретные проверки и минимальные изменения по `writing-plans`. Для бизнес-логики каждый такой шаг проходит Red → Green → Refactor.

## Этапы

- [x] **1. Основа API.** Проверить .NET 10 и доступ к Docker, создать решение с `src/MarketFlow.Api` и `tests/MarketFlow.Tests`. Подключить OpenAPI, Swagger UI и локальную тестовую PostgreSQL. **Готово**, когда собираются два проекта, тестовый хост отвечает и Swagger UI открывается. **Проверки** — сборка, тест доступности OpenAPI, соединение с тестовой БД.
- [x] **2. Справочники (MVP-1, MVP-2).** Добавить сущности, миграцию, создание и чтение товаров и складов, поиск товаров. **Готово**, когда весь контракт двух справочников проходит на чистой БД. **Тесты** — валидация, чтение, уникальность SKU, поиск, сортировка и пагинация.
- [x] **3. Остатки, приёмка и базовая история (MVP-3, часть MVP-5).** Добавить хранилище остатков и операций, атомарную приёмку, чтение остатков и истории. **Готово**, когда после приёмки виден ожидаемый остаток и одно движение, а повтор с тем же номером сохраняет результат. **Тесты** — повтор и конфликт номера, валидация, параллельные приёмки с одинаковыми и разными номерами, переполнение и откат. Для API чтения проверить фильтры, порядок и пустой результат.
- [x] **4. Резервирование (MVP-4, завершение MVP-5).** Добавить резерв и его движение в историю. **Готово**, когда резерв изменяет только зарезервированное и доступное количество, а история отражает оба типа операций. **Тесты** — точная граница доступности, недостаток и отсутствие остатка, изоляция складов, параллельные резервы, гонка приёмки с резервом и откат после обновления.
- [ ] **5. Воспроизводимый запуск и CI.** Собрать контейнер API и Compose, добавить пример окружения, запуск проверок в GitHub Actions и актуализировать README. **Готово**, когда с чистым томом разворачиваются база и API, а на повторном запуске данные сохраняются. **Проверки** — `docker compose config --quiet`, чистый и повторный запуск, сквозной сценарий через API, Swagger UI, `dotnet build` и `dotnet test`. Удалённый CI проверить при наличии согласованного репозитория и доступа.
- [ ] **6. Демонстрационная страница.** Добавить одну статическую страницу на HTML/CSS/JS в направлении C. Использовать готовый API для приёмки, резерва и чтения остатка. **Готово**, когда пройдены [критерии страницы](specs/mvp.md#демонстрационная-страница), а README объясняет запуск сценария. **Проверки** — повтор приёмки, результат 10/4/6, отказ при нехватке, клавиатура и узкий экран.
- [ ] **7. Финальная приёмка.** Сверить каждый пункт спецификации и принятые решения, повторить применимые проверки после последних изменений, записать результаты и оставшиеся ограничения. **Готово**, когда все согласованные критерии подтверждены и доступен воспроизводимый сценарий из README. Если проверка заблокирована средой, записать причину и точку продолжения.
