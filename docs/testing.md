# Стратегия тестирования

Один проект xUnit. Unit-тесты покрывают правила, которые работают без базы, например нормализацию и границы входных значений. Если правило реализовано средствами PostgreSQL или фреймворка, проверяем его через соответствующую границу. Моки EF Core, SQLite и EF InMemory не подтверждают семантику блокировок PostgreSQL. Цель — проверить риск, а не набрать процент покрытия.

**Red → Green → Refactor.** Напиши наблюдаемый критерий тестом и запусти его. Убедись, что он падает из-за отсутствующего поведения. Добавь минимум кода, запусти целевой тест, затем упрощай под защитой набора тестов. Для ошибки сначала воспроизведи её, проверь границы и найди причину, затем преврати воспроизведение в регрессионный тест. Для этого используй `systematic-debugging` и `test-driven-development` из Superpowers при доступности.

Интеграционные тесты поднимают ASP.NET Core через `WebApplicationFactory` и обращаются к настоящему PostgreSQL той же основной версии, что в Compose. Тесты получают отдельную базу, применяют миграции и изолируют данные между сценариями. В CI PostgreSQL работает сервисом. Локально используется тестовая БД в Docker. Нужные настройки и команды добавляются в README после первого рабочего запуска.

| Контракт | Минимальные сценарии |
| --- | --- |
| MVP-1 и MVP-2 | Валидные и невалидные POST, чтение по ID и `404`, повтор нормализованного SKU, буквальный поиск по части названия на кириллице и SKU в другом регистре, порядок и пагинация. |
| MVP-3 | Приёмка на пустом остатке и увеличение существующего. Неверное количество, неизвестные ссылки, повтор с теми же данными, конфликт с изменённым количеством или ссылкой, предел физического остатка. После ошибки проверить отсутствие новых строк и изменений. |
| MVP-4 | Частичный резерв и резерв всего доступного, отказ при недостатке, отсутствующий остаток, неизвестные ссылки, невалидное количество и независимость складов. |
| MVP-5 | Дельты и идентификаторы обеих операций, два фильтра вместе, детерминированный порядок и пагинация, пустые результаты и невалидный фильтр. |
| Атомарность | Для приёмки и резерва вызвать ошибку вставки истории после изменения остатка и операции, например временным триггером в изолированной тестовой БД. После ошибки через новое подключение убедиться, что остаток, факт операции и история остались прежними. После снятия сбоя повтор приёмки с тем же номером должен успешно пройти. |

## Гонки на PostgreSQL

Запросы используют независимые HTTP-запросы и транзакции. Общий сигнал старта позволяет отправить их вместе. Для целевого воспроизведения блокировки захватить строку остатка в отдельной транзакции, дождаться блокировки конкурентной команды по наблюдаемому состоянию PostgreSQL с таймаутом и отпустить строку. Не подменять синхронизацию произвольными задержками. После завершения всех запросов проверить HTTP-ответы, остаток, количество фактов и движений через новое подключение.

| Конкурентные запросы | Ожидаемый результат |
| --- | --- |
| Две одинаковые приёмки по 10 с одним номером | `201` и `200` с одним ID. В БД один факт, одна запись истории и физический остаток 10. |
| Две приёмки с одним номером и разными количествами | `201` и `409 supply_reference_conflict`. В остатке и истории только количество победителя. |
| Две первые приёмки по 10 и 6 с разными номерами на одной паре | Два `201`, два факта, два движения, одна строка остатка со значением 16. |
| Два резерва по 7 из 10 | `201` и `409 insufficient_stock`, зарезервировано 7, доступно 3 и создано одно движение резерва. |
| Поступление 3 и резерв 7 при исходном остатке 5 | Приёмка всегда увеличивает `onHand` до 8. Резерв успешен, если при условном обновлении видит приход. Иначе отказ сохраняет `reserved=0`. История соответствует результатам. |

Перед завершением MVP выполнить чистый Compose-запуск, пройти сценарий 10 → 4 → 6 через HTTP, проверить повтор и отказ, Swagger UI и сохранение данных после перезапуска. Фактические команды и результаты фиксируются в [журнале](progress.md).
